## 0. 상위 7단계와 실행 8단계의 관계

- **상위 정책:** `docs/OPERATING_PROCESS_v1.md`의 사용자·시장 조사 → 제품 기획 → UX/UI 설계 → 기술/데이터 설계 → 구현 → QA → 배포/학습 **7단계** 및 **G0 문제·고객, G1 기능 범위, G2 디자인·설계, G3 QA·배포, G4 실서비스화 승인**이 우선한다.
- **이 문서:** 이미 승인된 범위의 개별 작업을 반복 수행할 때 적용할 **8단계 실행/검사/기록 체크리스트**다. 새로운 기능·화면·수치·아키텍처·사용자 데이터 취급에 대한 **상위 Gate를 새로 부여하거나 생략하지 않는다**.
- G2 전체 HOLD는 모든 기능에 대한 신규 무제한 승인과 다르다. 기존에 개별 승인된 유지보수·프로토타입 작업은 승인 범위에서만 할 수 있으며, **전체 G2 HOLD 해제·main 병합·공개 배포는 별개로 판단**한다.
- 사용자 승인되지 않은 작업은 ②에서 HOLD. 대화의 `계속`·`굳`·버튼이 신규 Gate, main 병합, Pages/운영 배포, 공개 발송, 삭제, 결제, 유료플랜 변경, 실서비스 연동의 포괄 승인으로 해석되지 않는다.
- 이 저장소는 **공개(public)**다. 기능 브랜치, Draft PR, 커밋과 문서는 외부에서 열람 가능하며, **브랜치를 만들었다고 비공개가 되지 않는다**. 계정·키·연락처·의료기록·가입 증권·위치 정보 등 개인·민감 정보는 커밋하지 않는다.

## 1. 실행 계약

- **시작:** 사용자가 `다음 작업 이어서 하기` 터치 버튼을 누를 때마다 새 요청으로 시작한다. 정기·백그라운드 자동 개발은 아니다. 실행 횟수 제한이 없다는 말은 서비스 사용량 제한 면제를 뜻하지 않는다.
- **한 번의 완료 결과물:** 해당하는 경우 기능 코드·테스트, 기능 브랜치 Draft PR, 정확한 **최종 HEAD**의 전체 QA와 증거 링크, 변경/남은 문제/Gate/다음 작업을 기록한 인수인계, 사용자 보고 및 터치형 다음 버튼. **조사/설계/문서만 변경한 작업은 코드 변경·제품 QA '해당 없음'을 정직하게 기록**한다.
- **오류:** 각 단계의 불합격 원인을 먼저 기록한다. 원인 확인·수정 후 추가 재검사 **최대 2회**(최초 실패 + 재검사 2회). 연속 실패 또는 미확정 사실·승인 모호함·보안/보험 위험이 있으면 더 진행하지 않고 HOLD와 이유를 사용자에게 보고한다.
- **품질:** 소프트웨어 변경이 있으면 최종 HEAD의 관련 모든 GitHub Actions, Chromium·WebKit·axe, 기존 기능 회귀를 확인한다. Playwright WebKit은 실제 iPhone Safari 실기기 검증을 대체하지 않는다.
- **위험 동작 별도 승인:** main 병합, Pages·운영 배포, 공개 업로드·발송, 삭제, 결제·과금 변경, DB/Auth/실예약·실보험·개인정보 연동을 실행하기 전에 **해당 동작의 구체적 사용자 승인과 상위 Gate**를 모두 확인한다. G2 HOLD에서는 승인 없이 진행할 수 없다.
- **배포 사실 구분:** GitHub Pages는 `.github/workflows/pjm-012-pages-release.yml`의 **main 대상 `workflow_dispatch` 수동 실행, G3 승인 입력**을 사용한다. `main` 병합·Actions QA 성공·실제 Pages 배포 성공은 각각 다른 사건이다. 기존 GitHub 운영 상태는 매번 재조회한다.

## 2. 한 줄 흐름도

**버튼 시작 → ① GitHub 현황 → ② 승인 범위 → ③ 근거/보험 검증 → ④ 구현·테스트 → ⑤ 최신 HEAD 전체 QA → [실패 시 ⑥ 원인 수정 → ⑤ 재검사, 최대 2회] → ⑦ Draft PR·인수인계 → ⑧ Gate 승인 확인 → 결과 보고 + 다음 버튼**

- **통과:** 다음 단계. ⑤ 최초 합격이면 ⑥을 건너뛴다.
- **실패:** 실패 원인 명시 → 해당 단계에서 수정 → 최대 두 번 재검사. 두 번 실패하거나 불확실하면 작업 **HOLD**와 사용자 보고. ⑦에는 수행한 사실만 기록한다.
- **문서 전용 작업:** ④는 승인된 문서만 편집; ⑤는 Markdown/링크·변경 파일·기준 SHA·비밀정보·Gate를 검토. Chromium/WebKit/axe 등 **제품 QA는 '미실행/해당 없음(제품 코드 변경 없음)'**이지 '성공'이 아니다.
- **⑧ 승인 없음:** G2 전체 HOLD와 Draft PR을 유지하고, **미병합·미배포 상태가 정상적인 안전 종료**다.

- **하는 일/자료:** `main`의 SHA, 열린 Draft PR/HEAD, 정확한 SHA의 Actions, Pages 실행 이력, `AGENTS.md`, 상위 운영 문서, 최신 인수인계 확인.
- **바로 붙여 넣을 프롬프트:** "`jkd04255/peujima` 최신 main SHA, Draft PR 번호·HEAD, 필수 Actions 결과와 실행 SHA, 마지막 수동 Pages 실행 HEAD, AGENTS.md·운영 문서·인수인계를 실제 확인하세요. 확인하지 못한 정보는 미확인으로 기록하고 G2 전체 HOLD를 유지하세요."

- **이동:** 통과 → ③. 실패 → 범위 보완·재검사 최대 2회, 승인 경계 모호함 → HOLD·보고.

- **하는 일/자료:** 설계·코드·재현 사례와 공식 출처·적용 범위 대조. 보험사는 정확한 동물 종·가입 버전의 **상품 소개 vs 원문 약관·특약 vs 가입 증권**을 구분.
- **프롬프트:** "이번 변경에 필요한 `검증된 사실 / 출처 / 정확한 버전·적용 범위 / 미검증 사항`을 분리하세요. 보험료가 아닌 실제 의료비와 가정 보험금 산식을 확인하고, 미검증 비율·공제금·일/수술/연 한도·면책은 자동 프리셋에 임의 입력하지 마세요."

- **이동:** 통과 → ④(검증된 부분만). 근거 미확보 → 해당 수치 계산 차단 및 기록; 안전한 범위가 없으면 HOLD·보고.

### ④ 기능 코드와 테스트 구현하기

- **하는 일/자료:** 범위가 승인된 브랜치에서 최소 구현, 정상/오류/기존 기능 회귀 사례를 추가. 소스·테스트·디자인 기준·공식 근거 참고.
- **프롬프트:** "검증된 요구만 기능 브랜치에 반영하고, 제품 코드 변경 시 정상 1건·예외 1건·기존 회귀 1건 이상 자동 테스트를 추가하세요. Draft PR을 사용하며 기존 사진·3모드·지도·가상 예약·보험·진료비를 보존하세요. main 병합·Pages 배포는 하지 마세요."
- **검사(정해진 모양·개수):** 승인된 브랜치/파일만 변경되고, **제품 코드 변경이면** 정상·예외·회귀 테스트 각각 1개 이상. 문서 전용이면 변경 문서만 있으며 제품 테스트는 필수 아님.
- **이동:** 통과 → ⑤. 실패 → 범위/테스트 보완 최대 2회 후 HOLD·보고.

### ⑤ 정확한 HEAD로 전체 QA 실행하기

- **하는 일/자료:** PR HEAD, Actions 실행 SHA, Chromium·WebKit·axe·기존 회귀 결과 확인; 실제 기기 점검과 브라우저 자동화 구별.
- **프롬프트:** "최종 PR HEAD와 필수 GitHub Actions 실행 SHA를 정확히 비교하고 Chromium·WebKit·axe 및 관련 기존 회귀의 완료·성공 여부를 확인하세요. 테스트 누락·진행 중·다른 커밋 성공을 통과로 보고하지 마세요. 문서만 변경한 경우에는 문서 구조·링크·Gate·변경 파일 검증을 하고 제품 QA는 해당 없음으로 적으세요."
- **검사(숫자 맞추기):** **제품 코드 변경 시** 각 필수 실행 SHA = 최종 HEAD, 실패·미완료·누락 필수 QA **0건**. **문서만 변경 시** 링크·Markdown·경계 검사가 통과하고 제품 QA는 '미실행/해당 없음' 기록.
- **이동:** 합격 → ⑦. 실패 → ⑥. 판정 불가 → HOLD·보고.

### ⑥ 발견한 오류 수정·재검사하기 (필요할 때만)

- **하는 일/자료:** 실패 로그·재현 조건·최소 수정·재발 방지 테스트, 최신 HEAD 전체 재검사.
- **프롬프트:** "실패 이름·재현·원인·수정·현재 재시도 횟수를 기록하세요. 가장 작은 안전한 수정 후 최신 HEAD 기준 전체 QA ⑤를 다시 수행하세요. 수정 후 재검사는 최대 2회이며 해결되지 않거나 보험/승인 근거가 불확실하면 추가 변경을 멈추고 HOLD로 보고하세요."
- **검사(숫자):** 재검사 **최대 2회**·원인과 해당 HEAD 기록. 성공했다고 보고하려면 다시 ⑤의 조건을 충족.
- **이동:** 수정 → ⑤ 복귀. 두 번 실패 또는 중요한 불확실성 → HOLD 기록·보고(⑧의 위험 실행 금지).

### ⑦ Draft PR과 인수인계 기록하기

- **하는 일/자료:** PR·Actions·변경 파일/검증 결과를 기록해 다음 채팅에서도 정확히 이어가기.
- **프롬프트:** "Draft PR과 인수인계에 작업 ID, 변경 파일·내용, 최종 HEAD, QA 실행 SHA/링크 및 성공·실패·해당 없음, 미해결 문제, 승인 Gate, 다음 작업을 기록하세요. 기존 PR의 변경분을 덮거나 다른 브랜치 성과를 현재 성과로 표현하지 마세요."
- **검사(꼭 들어갈 것):** `작업 ID·HEAD·변경 내역·QA 증거·미해결·Gate·다음 계획` **7개 항목**.
- **이동:** 통과 → ⑧. 실패 → 누락 기록 보완 최대 2회 후 HOLD·보고.

### ⑧ 병합 및 배포 승인 확인하기

- **하는 일/자료:** 최신 G2 Gate, 사용자 작업별 명시적 승인, 실제 QA, Pages 수동 배포 정책 대조.
- **프롬프트:** "main 병합·Pages/운영 배포·공개 업로드/발송·삭제·결제·과금 변경·실보험/실예약/DB/Auth 연동을 실행하기 전 상위 Gate 충족과 해당 동작의 구체적인 승인 여부를 확인하세요. G2 전체 HOLD이면 별도 승인 없이 위험 작업을 실행하지 말고 미병합·미배포 상태로 보고하세요. 결과와 다음 작업 터치 버튼을 제공하세요."
- **검사(정해진 모양):** 승인·Gate·QA가 충족된 동작만 실행. 그 외에는 **승인 없는 위험 작업 0건**과 HOLD 사유가 기록됨.
- **이동:** 통과 → 결과 보고·다음 작업 버튼. 위험 또는 미승인 → 즉시 중단·보고. 이 단계의 '통과'는 반드시 병합/배포를 뜻하지 않는다.

## 4. 보험 약관·보험금 계산 전용 하위 절차

③에서 아래를 확인하고 ④에서 코드·테스트에 적용한다. **보험의 정확성은 일반 화면 QA 성공만으로 보장되지 않는다.**

1. **보험사·종·가입 버전 확인하기:** 반려견/반려묘, 제품명, 개정 버전, 선택 플랜, 기본 담보·특약을 서로 묶고 다른 상품·종·버전 값을 복사하지 않는다.
2. **공식 조건과 면책 검증하기:** 보상비율, 자기부담금, 일/수술/연간 한도, 연간 잔여한도, 최초 보장개시·면책기간, 통원/입원 범위, 특약 가입 여부, 동일일·중복 지급 제한을 검토한다.
3. **출처의 신뢰도를 구별하기:** **A** 정확한 버전의 보험사 원문 약관/특약과 선택 담보 근거, **B** 보험사 공식 상품 소개에서 확인한 일부 비율/공제금, **C** 홍보·보도자료, **D** 제3자·근거 부재/버전 혼합. B는 A의 완전한 검증으로 승격하지 않는다. 개인 증권·청구 심사 없이 개인의 보험금 지급을 확정하지 않는다.
4. **진료비와 지급 산식 검증하기:** 비용의 공식 중간값·사례 참고·예산 추정을 구분한다. 검증된 의료비 대상 범위에서 `max(0, 해당 보장 대상 비용 - 자기부담금) × 보상비율` 및 확인된 한도·소수점 처리·중복 공제를 적용한다. 실제 담보별 산식이 이와 다르면 해당 약관을 우선한다. 여러 날의 치료비를 임의로 1일 청구처럼 합산하지 않는다.
5. **확인된 범위만 계산하기:** **0원 보험금 가능성**, 면책·특약 미가입·한도 소진·기지급금·보험사 심사·비적용 진료를 명시한다. 미확인 한도·비율은 자동 지급액에 넣지 않고, 사용자 직접 입력값은 **개인 가정**으로 표시한다.
6. **경계 회귀 실행하기:** 보험사·동물 종·가입 버전 혼합 방지, 2607↔2610, 공제·반올림·한도 0/경계, 다른 진료/특약과 동일일 중복, 다일 치료·예방/기타 보장 제외, 화면 320/390/1440px·WebKit/접근성·기존 회귀를 검사한다. 기능 코드가 바뀌었다면 마지막 HEAD의 ⑤ QA로 복귀한다.

**보험 전용 단일 합격 검사:** 보험사·종·상품 버전·출처/등급·보상비율·공제금·해당 담보/한도·면책의 **확인/미확인 여부가 전부 명시**되고 미검증 수치의 **확정 지급액 표시가 0건**이면 합격. 모든 보험사 약관 미확보 시에도 정확히 차단한 상태는 합격할 수 있으며 실제 보험금의 정확성이 전부 검증됐다는 뜻은 아니다.
