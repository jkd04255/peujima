# PRZIMA 운영 프로세스 v1.0
상태: 적용 시작 (2026-11-07) · 범위: 프지마 프로토타입 및 향후 개발
소유자: 사용자(Product Owner) · 실행 담당: ChatGPT(기획/설계/구현/테스트 보조)

## 채택한 외부 방법론
- Design Council Double Diamond: 발견(Discover) → 정의(Define) → 개발(Develop) → 전달(Deliver)
  https://www.designcouncil.org.uk/resources/framework-for-innovation/
- Atlassian Agile/Scrum: 우선순위가 정해진 백로그, 짧은 스프린트, 리뷰 및 회고
  https://www.atlassian.com/agile/scrum/sprints
- GitHub Flow: 기능 브랜치 → 커밋 → Pull Request 검토 → 병합
  https://docs.github.com/en/pull-requests/get-started/about-pull-requests
- W3C WCAG 2.2: 접근성 품질 참고 기준
  https://www.w3.org/TR/WCAG22/

프지마는 1인 기획자 + AI 개발 파트너이므로 과도한 회의 대신 산출물/승인 중심의 경량 프로세스를 채택한다.

## 전체 프로젝트 7단계
| 단계 | 해야 할 일 | 산출물 | 승인 게이트 |
| --- | --- | --- | --- |
| 1. 사용자/시장 조사 | 사용자 문제, 병원 제휴 현실성, 경쟁 대안 조사 | 문제정의·가설·조사기록 | G0 — 문제와 대상 고객 동의 |
| 2. 제품 기획 | 시나리오, 기능 범위, 우선순위, 성공 기준 | PRD·백로그·인수기준 | G1 — 기능 범위 승인 |
| 3. UX/UI 설계 | 사용자 여정, 화면 흐름, 모바일/PC 와이어프레임 | 화면 흐름도·시안 | G2 — 화면과 카피 승인 |
| 4. 기술/데이터 설계 | 모델, 예외상태, 접근성·개인정보·연동 위험 | 기술설계·데이터 스키마·위험표 | G2 재검토(중대한 구조 변경일 때) |
| 5. 구현 | 기능 브랜치에서 제한된 범위만 코드 작성 | 코드·커밋·PR | — |
| 6. 품질검증 | 기능·회귀·모바일·접근성·오류·시연 정책 검증 | QA 체크리스트·스크린샷·결함 | G3 — 배포 승인 |
| 7. 배포/학습 | main 병합, Pages 배포 확인, 피드백 수집 | 배포·롤백 기록·회고 | G4 — 실제 서비스화 여부 별도 승인 |

단계는 가설이 틀리면 이전 단계로 돌아가 수정할 수 있으며, 직선적으로 한 번만 진행하는 절차가 아니다.

## 기능 단위 표준 개발 순서
1. IDEA: 사용자 요청을 백로그에 기록한다(기능/버그/디자인/조사 구분).
2. DISCOVER: 해결할 사용자 문제, 필요성, 대안, 제휴/법적 위험을 검토한다.
3. SPEC: docs/templates/FEATURE_SPEC.md 형식으로 요구사항과 인수기준(AC)을 1페이지로 작성한다.
4. G1: 사용자가 범위와 우선순위를 승인한다. 사소한 스타일 수정은 대화상의 명시적 요청을 승인으로 간주할 수 있다.
5. DESIGN: 변경 전/후 화면 흐름과 모바일 시안을 제시한다.
6. G2: 사용자 승인 후 코드 구현한다. 기존 승인된 디자인과 기능을 유지한다.
7. BUILD: 기능별 브랜치 생성 후 국소적 구현. GitHub main에 직접 밀어넣지 않는 것을 기본값으로 한다.
8. QA: 자동/수동 테스트, 실제 기기 확인 가능 여부, 발견한 한계를 기록한다.
9. G3: PR·QA 결과·스크린샷으로 배포 승인을 받는다. 긴급 핫픽스는 위험 설명과 사용자 승인 하에 예외 가능.
10. RELEASE: 승인 후 main 병합 → GitHub Pages 반영 확인 → 버전/변경 기록 작성.
11. REVIEW: 실사용자 피드백, 오류, 개선점을 백로그에 반영한다.

GitHub Pages는 main을 공개하므로 main에 병합하면 곧바로 공개 사이트가 변경된다. 테스트 브랜치와 승인되지 않은 배포를 명확히 구분한다.

## 역할과 책임
| 역할 | 책임 |
| --- | --- |
| 사용자 / Product Owner | 가치 판단, 기능 우선순위, G1/G2/G3 승인, 외부 병원 제휴 결정 |
| ChatGPT / PM·UX·개발 보조 | 요구사항 초안, UX 설계, 기술 선택, 코드·테스트, 작업 기록 |
| 검증 사용자(추후) | 보호자/병원 관점 사용성 테스트 및 피드백 |

동일한 AI가 코드 작성과 QA를 수행하므로 독립적 코드 리뷰가 아니라는 한계를 명시한다. 외부 테스터 참여나 사용자의 실제 모바일 확인으로 보완한다.

## 정의(Definition of Ready)
- 어떤 사용자가 어떤 상황에 쓰는지 한 문장으로 설명 가능
- 포함/제외 범위 명시
- 검증 가능한 인수기준(AC) 2개 이상
- 실제/가상 데이터 구별, 관련 위험 기록
- 요청한 디자인 변경이면 승인 기준선 또는 참고 화면 확보

## 정의(Definition of Done)
- 인수기준 모두 충족 또는 미충족 항목 명시
- 모바일 320/390/768px, PC 1440px 화면 점검(가능한 환경에서)
- 강아지/고양이/전체 모드와 7일 예약·수의사·기타 입력·완료·보험 이동 회귀 점검
- 키보드 사용/레이블/대비 등 WCAG 2.2 참고 검사
- 오류·콘솔·가로 넘침·미접속/빈 데이터 등 예외 검사
- PR 변경내용과 스크린샷, QA 결과, 남은 문제 기록
- 사용자가 승인한 경우에만 공개 배포
- 실제 병원/보험 연동이 없는 시연임을 명확히 표시

## 중요한 정책
- 현재 v0.5.2는 프로토타입이다. 실제 병원·진료 슬롯·예약·보험 적용 결과로 오해하게 해서는 안 된다.
- 실제 예약 접수, 의료 정보 저장, 위치 추적, 보험사 API, 결제, 사용자 인증은 별도 타당성 검토 및 승인 필요.
- 개발 완료 = 배포 완료 = 실제 서비스 운영을 혼동하지 않는다.
- 앞으로 모든 응답의 마무리에는 '완료된 일 / 검증 / 보류 / 사용자 다음 행동'을 짧게 명시한다.
